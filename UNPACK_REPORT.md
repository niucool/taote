## The two systemic defects behind the remaining gap

**1. The OEP pick, not the decode.** 0 samples have a wrong entry
(0 of them inside the original's entry section, i.e. the right code region
and the wrong address) while the payload itself is recovered: the code
similarity medians at 1.000 for ASPack, Eronana, Packman, JDPack, MPRESS and
Molebox. The dominant shape is the MSVC CRT-init thunk
(`e8 <call __security_init_cookie>; e9 <body>`) - the packer preserves the
*thunk* as the entry, so a picker that lands on the body, on another
prologue, or on the last accepted hop is wrong even though the bytes are
right. Fixing the picker is worth more samples than any decoder work.

**2. The IAT selection for a few families.** RLPack is the clean example:
`rlpack_ADExplorer.exe` decodes to sim 0.978 with the exact EP, but its
rebuilt table has 16 descriptors / 85 entries and reproduces only 17 of the
original's 314 imports - it kept the *stub's own* table (`wldap32`,
`mspdb80`, `hhctrl.ocx` are the stub's delay-load helpers) instead of the
payload's, and misses 109 kernel32 + 99 user32 functions. That is the
Scylla-style 'which table does the code reference' step, which the harness'
DLL-coverage rubric cannot see.

Measured separately: emitting ordinal imports in their real form
(`0x80000000|ord`) instead of as `"ordinal_N"` hint/name strings moved the
whole corpus from 853 to 1076 samples passing all three criteria (criterion
3: 48.9% -> 60.6%), with the decode untouched.

### What criterion 3 is losing

The misses are not random. On the reference program `AccessEnum.exe` (232
imports) the rebuilt tables carry 440 entries yet miss 12, and **all 12 are
ordinal imports** (`oleaut32!#2`, `#6..#12`, `#150`, `#200..#202`, `#94`,
`comctl32!#17`). The same 12 show up missing for *every* packer of that
program, so it is one rebuild rule, not per-family decoding: the import
rebuilder emits hint/name entries only and drops the `0x80000000|ordinal`
form. A DLL-coverage rubric cannot see this (oleaut32 is still 'covered').
